# Commutator: разработка и релизы

Пользовательская документация — в [README.md](README.md). Черновики, планы и разборы для себя кладите в `local/`: эта папка в `.gitignore`, в репозиторий она не попадает.

## Подготовка Mac (один раз)

Нужен полный Xcode из App Store, Command Line Tools не хватит: `actool` из Xcode собирает значок приложения в строке меню.

```sh
sudo xcode-select -s /Applications/Xcode.app
brew install go automake pkg-config openssl@3 lzo lz4 gh
gh auth login                   # вход в GitHub, откроется браузер
```

## Выпустить релиз

```sh
make version V=1.1.0            # 1. новая версия
git commit -am "Commutator 1.1.0" && git push   # 2. в git
make release NOTES="Что нового"  # 3. сборка и публикация
```

Установленные копии узнают о релизе сами: при запуске и раз в 6 часов они спрашивают `api.github.com/…/releases/latest`, показывают уведомление и кнопку в тулбаре окна, а по ней ставят новый pkg. Подробнее в разделе [«Обновление из приложения»](#обновление-из-приложения).

**Шаг 1.** `make version` меняет версию сразу в обоих местах, где она живёт: в `Config/AppInfo.plist` (плюс номер сборки +1) и в `VPNRouterVersion.current` в `Sources/VPNRouterCore/Models.swift`. Если версии расходятся, приложение при каждом запуске переустанавливало бы системную службу с паролем, поэтому сборка pkg такое не пропустит.

**Шаг 2.** Коммит и push остаются за вами: релиз публикуется ровно из того кода, что лежит на GitHub. `git commit -a` не берёт новые файлы: сначала проверьте `git status` и добавьте их через `git add`.

**Шаг 3.** `NOTES` — описание релиза для пользователей. Его видно на странице Releases и в приложении по кнопке «Что нового», поэтому пишите по-русски и для людей, а не для разработчиков. Пишите коротко: что нового и что исправлено. Работает Markdown, для многострочного текста используйте `NOTES="$(cat local/заметки.md)"`. Остальное `make release` делает сам:

1. Создаёт сертификат подписи «Commutator Local Development», если его ещё нет. При первом запуске macOS попросит пароль от связки ключей. Зачем он нужен — в разделе [«Подпись»](#подпись).
2. Собирает движки (openvpn, amneziawg-go, awg, xray), только если их нет или в `scripts/build-vpn-tools.sh` поменялась версия. Первый раз это займёт минут десять.
3. Прогоняет тесты.
4. Собирает `Build/Commutator.app` и упаковывает его в `Build/Commutator.pkg`. Попутно проверяет, что сборка подписана и версии совпадают.
5. Проверяет, что всё закоммичено и запушено.
6. Публикует GitHub Release.

### Как pkg попадает в GitHub Releases

```mermaid
flowchart LR
    M["make release<br/>на вашем Mac"] --> P["Build/Commutator.pkg"]
    P -- "gh release create v1.1.0" --> R["GitHub Release v1.1.0<br/>тег v1.1.0 на вашем коммите"]
    R --> L["…/releases/latest/download/Commutator.pkg<br/>ссылка из README"]
    L --> F["пользователь скачивает"]
```

Последний шаг выполняет `gh`, консольный клиент GitHub. Он создаёт на GitHub релиз `v1.1.0`, ставит тег `v1.1.0` на текущий коммит и прикладывает к релизу файл `Commutator.pkg`. Описанием релиза становится текст из `NOTES`. Имя файла одинаковое во всех версиях, поэтому ссылка `releases/latest/download/Commutator.pkg` в README всегда ведёт на самую свежую.

Без `gh` то же можно сделать руками. Выполните `make installer`, откройте на GitHub **Releases → Draft a new release**, впишите тег `v1.1.0`, перетащите `Build/Commutator.pkg` в поле для файлов и нажмите **Publish release**.

### Первая публикация

```sh
git init -b main
git add . && git status          # не должно быть .build, Build, Vendor/sources, local/
git commit -m "Commutator 1.0.6"
gh repo create commutator --public --source . --push
make release NOTES="Первый публичный выпуск"
```

## Команды

| Команда | Что делает |
|---|---|
| `make release` | Всё от сборки до публикации, см. выше |
| `make version V=x.y.z` | Поднять версию в обоих местах |
| `make test` | Тесты. Сеть и системную службу не трогают |
| `make app` | Собрать `Build/Commutator.app` |
| `make install` | Поставить сборку себе в `/Applications`, пароль один раз. Запущенный Коммутатор сначала закрывается |
| `make installer` | Только собрать `Build/Commutator.pkg`, ничего не публикуя |
| `make tools` | Принудительно пересобрать движки |
| `make setup-signing` | Создать сертификат подписи, если его нет |
| `make icon` | Пересобрать иконку из `Config/IconArtwork.png` |

В интерфейсе macOS (Finder, Dock, меню, системные запросы) приложение называется «Коммутатор»: это имя задаёт `Config/ru.lproj/InfoPlist.strings`. Файл при этом остаётся `Commutator.app`, потому что латинский путь нужен установщику и скриптам. `CFBundleDisplayName` в `Config/AppInfo.plist` должен совпадать с именем файла, иначе Finder не подставит русское имя.

`BUNDLE_ID` по умолчанию `com.vpnrouter.app` и переопределяется при сборке. Внутренние идентификаторы (`com.vpnrouter.*`, `VPNRouter*`, `VPNROUTER_*`) остались от прежнего названия и специально не меняются: иначе обновление поверх установленной версии сломается.

## Подпись

Без сертификата сборка получается ad-hoc, и системная служба принимает команды от любой программы на Mac. Поэтому `make installer` и `make release` такую сборку не упакуют. Для своей машины она годится: `make install` работает и без сертификата, только «Изменить…» профиля будет каждый раз спрашивать пароль администратора.

С сертификатом служба проверяет, что команду прислал именно Коммутатор. Она сверяет отпечаток сертификата из подписи, а не доверие к нему, поэтому проверка работает и на чужом Mac, где этот сертификат никому не известен. Для Gatekeeper сборка остаётся неподписанной: отсюда шаг «Всё равно открыть» при установке.

**Сохраните копию сертификата:** «Связка ключей» → «Commutator Local Development» → «Экспортировать…» → `.p12`. Если он потеряется, `make release` создаст новый с другим отпечатком. Установка pkg поверх это переживёт, но macOS может заново спросить у пользователей разрешение на уведомления, а кнопка обновления в приложении откажется ставить такой релиз: этот один раз пользователям придётся поставить pkg вручную. Чтобы собирать на другом Mac, импортируйте туда `.p12`.

## Движки

Пользователям ничего собирать не нужно: всё уже внутри pkg. Сборка движков — аналог `npm install`, но нужна только вам и только один раз на версию. Готовых пакетов для этого нет: openvpn под macOS официально распространяется только исходниками, а версия из Homebrew зависит от библиотек Homebrew, которых у пользователей нет. `scripts/build-vpn-tools.sh` собирает статические arm64-бинарники из закреплённых тегов и кладёт рядом архивы исходников, как того требует GPL.

**Обновить движок:** поменяйте тег в `scripts/build-vpn-tools.sh` и в [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md). `make release` сам пересоберёт движки и остановится на незакоммиченном `Vendor/SHA256SUMS`: закоммитьте его, запушьте и запустите `make release` ещё раз.

## Иконка

Исходная картинка лежит в `Config/IconArtwork.png` (квадрат с прозрачным фоном). `scripts/make-icon.swift` кладёт её на светлую скруглённую плашку по сетке иконок macOS. Размер картинки на плашке задаёт `artworkSide` в начале скрипта. После замены картинки или правки скрипта выполните `make icon`. Результат (`Config/AppIcon.icns`, `Config/AppIcon.png` для README) коммитится.

Значок Коммутатора — свои SF Symbols в `Config/Symbols.xcassets`. В строке меню: `kommutator.bar.off` (выключен и подключается), `kommutator.bar.on` (работает; рычаг зелёный, при частичной работе жёлтый), `kommutator.bar.error` (рычаг красный). Они без боковых полей и крупнее, а высота подобрана так, чтобы значок не выходил за строку меню и на мониторе без Retina. У пункта «Обзор» — `kommutator.off`, шириной с соседние символы, чтобы подписи стояли ровно. Это шаблоны символов: рычаг — основной слой, основание — второй. `scripts/build-app.sh` собирает каталог через `actool` в `Contents/Resources/Assets.car`. Шаблон можно открыть и поправить в приложении SF Symbols; плоские контуры без градиентов и фильтров, варианты Ultralight-S, Regular-S и Black-S.

## Что делает установщик

Системная служба и VPN-бинарники входят в сам `.app`. Postinstall пакета копирует службу в `/Library/PrivilegedHelperTools/com.vpnrouter`, регистрирует её в launchd, снимает карантин с приложения и запускает его от имени вошедшего пользователя. Всё это происходит внутри той единственной авторизации, которую запросил установщик macOS.

Если приложение скопировали в `/Applications` вручную, минуя pkg, оно поставит службу само при первом запуске и спросит пароль. Если его скопировали поверх старой версии, при запуске оно заметит службу другой версии и заменит её. Если установку отменили, в окне будет кнопка «Установить…». Сборка с Developer ID вместо этого регистрирует службу через `SMAppService` (System Settings → General → Login Items).

### Обновление из приложения

Приложение проверяет `releases/latest` при запуске и раз в 6 часов (`AppModel.watchUpdates`). Сравнение версий и разбор ответа — `AppRelease` в Core. Черновики и pre-release GitHub сюда не отдаёт, релиз без `Commutator.pkg` не предлагается. Каждый шаг — кнопка пользователя:

1. «Скачать» кладёт pkg и описание в `~/Library/Caches/<bundle id>/Update`. Скачанное переживает перезапуск приложения и удаляется, когда версия установлена.
2. «Обновить и перезапустить…» спрашивает, можно ли выключить VPN, и выключает его через старую службу, как обычный переключатель. Уборка туннелей, PF и DNS не зависит от 20 секунд, которые launchd даёт службе при остановке. Затем приложение перестаёт опрашивать службу и отправляет ей `installUpdate` с путём к pkg. Пароль не нужен: ставит служба (`RouterDaemon.installUpdate`), она уже работает от root. Служба:
   - принимает запрос только от клиента с подписью Коммутатора (обычная проверка XPC);
   - отказывает, пока предыдущая установка ещё идёт;
   - копирует pkg в `/var/db/com.vpnrouter/update` (доступ только у root) и распаковывает его. Символическая ссылка в распакованном pkg — отказ: через неё проверку можно направить в папку пользователя;
   - сверяет подпись Commutator.app с тем же требованием, по которому проверяет клиента (identifier плюс отпечаток сертификата или Team ID);
   - ставит только версию новее своей, без откатов назад;
   - запускает `install-update.sh` из **проверенного** бандла разовой задачей launchd `com.vpnrouter.update`. Скрипты самого pkg не выполняются. Отдельная задача нужна потому, что скрипт вызывает `install-system-component.sh`, а тот останавливает службу, и её дочерний процесс погиб бы вместе с ней.

   Скрипт копирует приложение во временную папку со случайным именем в `/Applications`, отодвигает старое и ставит новое на его место. Если что-то сорвалось, старое возвращается. Затем скрипт ставит новую службу, запуская `install-system-component.sh` из проверенной копии, а не из `/Applications`: туда может писать любой процесс администратора. Старое приложение ждёт, пока ответит служба новее его самого (до трёх минут), затем выходит и открывает новое. Пока идёт установка, приложение не шлёт службе настройки, профили и переключатель. Обновляется только копия `/Applications/Commutator.app`: копию в другом месте кнопка не обновит, она предложит pkg. Новое включает VPN, если стоит отметка `resume-after-update` в UserDefaults.

Безопасность держится на подписи. Кто получит сертификат «Commutator Local Development», сможет поставить что угодно на все Mac с Коммутатором без пароля, поэтому храните `.p12` так же бережно, как ключ. Ad-hoc сборку служба так не обновляет, у неё нет требования к подписи. Новая служба читает `state.json` старой, поэтому новые поля в нём только необязательные.

Кнопка «Удалить Коммутатор…» (внизу «Общих») просит службу удалить всё без пароля (`RouterDaemon.uninstall`). Служба принимает запрос только от подписанного клиента, удаляет только `/Applications/Commutator.app` (путь сверяется после раскрытия ссылок), сверяет его подпись и запускает разовую задачу launchd `com.vpnrouter.uninstall`. Задача выполняет копию `scripts/uninstall.sh`, которую `install-system-component.sh` кладёт в `/Library/PrivilegedHelperTools/com.vpnrouter`, куда пишет только root. Отдельная задача нужна потому, что служба при остановке пишет журнал и сохраняет состояние, и удалённые файлы появились бы снова. Перед этим приложение выключает VPN через службу, как при обновлении. Если служба отказала (ad-hoc сборка, служба старой версии или её нет, копия не в «Программах», служба зарегистрирована через SMAppService и копии скрипта рядом нет), приложение запускает `uninstall.sh` из бандла с паролем администратора. Скрипт останавливает службу (по SIGTERM она сама возвращает DNS, PF и маршруты) и удаляет всё, что поставил установщик. Новый системный файл — добавьте его туда же.

## Устройство

- `VPNRouterApp` — окно, меню, уведомления и XPC-клиент.
- `VPNRouterDaemon` — root-служба: management-сокеты OpenVPN, проверка handshake AmneziaWG, Xray и подписки, DNS-прокси, свои маршруты и PF anchor `com.apple/vpn-router`.
- `VPNRouterCore` — модели, разбор профилей, DNS и CIDR, чистый генератор правил PF.

**Подключения и направления.** Подключение (`StoredConnection` в daemon, `ConnectionSummary` в приложении) — один сохранённый VPN: профиль OpenVPN, профиль AmneziaWG или ссылки/подписка Xray. Направление (`Direction` в `RouterSettings`) — это название, путь, для подписки выбранный сервер, правила и kill switch (`blockWhenDown`). Путь бывает `.direct`, `.vpn(id подключения)` или `.unset` («VPN не выбран»): такое направление не запускается и никогда не считается «напрямую». Сервер подписки хранится как `ServerChoice` — по имени, хосту, порту и протоколу, потому что индекс меняется при обновлении (порт и протокол необязательны: выбор, сохранённый без них, находит первый сервер с таким именем и хостом; сравнивает `ServerChoice.matches`). Названия направлений не повторяются (без учёта регистра): экспорт и импорт различают направления только по названию. Направление для остального трафика — `defaultDirection`. Настройки хранят и приложение (UserDefaults), и daemon; приложение отправляет свои при каждом запуске (`updateRules`).

**Туннели.** На каждое включённое направление с VPN — туннель со своим id: для OpenVPN и AmneziaWG это id подключения, для Xray — id подключения плюс хост, порт, протокол и имя сервера. Направления на одном VPN и сервере делят туннель, два сервера одной подписки — два туннеля. `TunnelSupervisor` держит сколько угодно туннелей. У каждого свой номер (slot): по нему названы файлы в `/var/run/com.vpnrouter`, строки журнала (`openvpn:1`) и адрес TUN у Xray (`198.18.0.1/30`, `198.18.0.5/30`, …).

Изменение направлений перезапускает только туннели, у которых поменялось то, что они запускают: профиль, сервер, пароль, первый сервер OpenVPN (см. `TunnelPlan.fingerprint`). Смена правил туннели не трогает — только маршруты и PF. Смена сети по-прежнему перезапускает всё.

**Приоритет.** Всё решает порядок направлений в списке: выигрывает верхнее совпавшее направление, даже если правило ниже точнее (`RuleSet.classify`). Так же устроены PF (таблицы направлений идут по порядку, после каждой — `block drop`) и маршруты: сеть нижнего направления внутри сети верхнего маршрут не получает (`RouteController.routes(for:)`). Иначе ядро выбрало бы её как более длинную, а PF отбросил бы трафик. Сети и домены, присланные OpenVPN-сервером, и строки `route` из профиля относятся ко всем направлениям этого подключения. Последнее, что прислал сервер, daemon хранит в подключении (`StoredConnection.pushed`, со временем) и показывает и после отключения; маршруты при этом строятся только из присланного в текущем подключении. Если у VPN нет своего DNS, имена направления спрашиваются у DNS сети — выключить это нельзя, иначе направление не работает. User-Agent подписок один на всех (`RouterSettings.subscriptionUserAgent`); после его смены daemon сразу перезагружает подписки.

**Направления по умолчанию.** Новая установка начинается с трёх направлений под фиксированными `LegacyIDs`: «Работа» (work), «Личный» (personal, для остального трафика), «Напрямую» (direct, `.ru`, `.su`, `.рф`) — `RouterSettings()`. «Работа» и «Личный» без VPN — `.unset` и выключены, иначе «Включить» отказал бы: направление включено, а работать не может. Выбор VPN в пустом направлении включает его. Настройки до направлений переводятся в эти же три (перенос 1.0.7). Направление для остального трафика не получает правил (`RoutingDraft.applied`), но его текст приложение хранит в UserDefaults `simple-parked` по id направления (`RoutingDraft(settings:parked:)`), так что отметка «для остального трафика» туда и обратно список не стирает. «Добавить новый VPN…» в редакторе направления ставит новый VPN в это направление (`AppModel.addVPN(for:)` → `adopt(_:into:)`), а прежний профиль предлагает удалить, если его больше никто не использует (`retire`). VPN, добавленный без кнопки, встаёт в ожидающее направление (`AppModel.adopt`). Перенос 1.0.7 направляет «Работу» и «Личного» на фиксированные id, даже если такого профиля не было; до первой синхронизации с daemon такие пути становятся `.unset` и выключаются (`RouterSettings.droppingMissing`, `AppModel.dropMissingVPNs`), иначе daemon отклонил бы настройки. Ключи `simple-mode` и `router-settings-other` остались от dev-сборок с двумя режимами; приложение их стирает.

**Миграция.** Настройки и `state.json` от 1.0.7 и раньше читаются и переводятся в направления с фиксированными id (`LegacyIDs`): приложение и daemon мигрируют каждый свою копию и должны прийти к одинаковым направлениям. Рабочий профиль становится «Работой», список direct вместе с галочками зон — «Напрямую», личный VPN — «Личным» (для остального трафика; `blockWhenDown` берётся из бывшего kill switch). Запасные профили становятся подключениями со своими прежними id. Записываются уже только новые поля, поэтому старая версия новый `state.json` не поймёт. `LegacyIDs` не менять.

**DNS** раскладывается по направлениям: имя уходит в DNS того направления, которому принадлежит. У OpenVPN это DNS, присланный сервером, у AmneziaWG — `DNS =` из профиля, у Xray — 1.1.1.1 и 8.8.8.8, у направлений без VPN — DNS текущей сети. Имена серверов VPN всегда спрашиваются у DNS текущей сети.

Адреса DNS направления с VPN попадают в его таблицу и маршруты, поэтому запросы к ним идут через его туннель. Если два направления называют один и тот же DNS, он достаётся верхнему. Пока туннель не поднялся, прокси отвечает SERVFAIL, если направление блокирует при падении, иначе спрашивает DNS сети.

Если у VPN остального трафика есть свой DNS, системный resolver на время работы переключается на локальный прокси и восстанавливается при выключении. Иначе прокси получает только имена из правил, через `/etc/resolver`. Если переключить resolver не удалось, включение завершается ошибкой и откатывается целиком: иначе статус «Работает» показывался бы, пока имена по-прежнему уходят в DNS сети.

Локальный прокси слушает `127.0.0.1:53`: `networksetup -setdnsservers` принимает только адрес без порта, поэтому другого способа увести системный resolver на прокси нет. Если порт занят чужим резолвером, включение завершится ошибкой, а системный DNS останется нетронутым. В каждом классе перебираются до двух серверов: если первый не ответил за 2 секунды, запрос уходит второму, и только потом клиент получает SERVFAIL. Третий и следующие серверы не используются. Для имён из правил прокси урезает TTL ответа до 60 секунд: столько daemon держит связку «адрес → направление» после последнего ответа, и кеш macOS или программы не должен её пережить. Пока к адресу есть открытое соединение, связка не снимается: раз в 30 секунд daemon смотрит `netstat -an`.

**Журнал.** Полный журнал подключений служба пишет в `/var/log/vpn-router.log` (root, `0600`; при 8 МБ обрезается с сохранением свежей половины): вывод openvpn, amneziawg-go и xray, обмен с management-сокетом, шаги запуска и остановки, причины падений туннелей, раз в полминуты — строка состояния. amneziawg-go запускается с `LOG_LEVEL=verbose`, иначе он молчит и по логу нельзя отличить рукопожатие без ответа от пакета, который зарубил наш же PF; строки про keepalive отбрасываются при чтении. Последние 10 000 строк приложение держит в памяти, а в «Диагностике», вкладка «Журнал», показывает последние 20/50/100/200 (по умолчанию 20, с учётом поиска). «Скопировать» берёт ровно показанные строки и добавляет сверху сводку: версии приложения и службы, состояние направлений, macOS, `hw.model` и типы VPN — без названий подключений (`AppModel.copyDiagnostics`).

**Обезличивание журнала.** Журнал пишется, чтобы его отправляли на разбор, поэтому `LogRedactor` (в Core, тестируется) заменяет имена серверов и публичные адреса устойчивыми псевдонимами `хост#N` и `адрес#N`: один и тот же адрес всегда получает тот же псевдоним, поэтому маршрут, правило PF и рукопожатие по-прежнему связываются между собой. Почта и поля сертификатов скрываются целиком, длинные ключи обрезаются до четырёх символов. Имена заменяются только зарегистрированные (`TunnelLog.register(host:)` — серверы профилей, endpoint AmneziaWG, серверы и хост подписки), иначе под замену попали бы `com.vpnrouter` и `openvpn.conf`. Частные адреса, имена интерфейсов, маски сети, порты и коды ошибок остаются как есть — без них журнал бесполезен. `VPNROUTER_LOG_RAW=1` отключает обезличивание, только для ad-hoc dev-сборки. Имена сайтов, которые резолвит пользователь, в журнал не попадают вообще: это была бы история посещений.

**Сон и пробуждение.** Отдельных системных уведомлений о сне служба не слушает: сигналом служит событие сети, а сам факт сна виден по разрыву между тиками обслуживания («Похоже, был сон»). После пробуждения последнее рукопожатие AmneziaWG всегда просрочено, поэтому запас в 35 секунд отсчитывается не от запуска туннеля, а от момента, когда рукопожатие впервые оказалось просроченным — WireGuard успевает восстановиться сам, без перезапуска движка. Для OpenVPN ограничение на подключение взводится заново при каждом мягком перезапуске (90 секунд): иначе переподключение после пробуждения могло висеть бесконечно, и никто за ним не следил.

**Трафик.** Вкладка «Трафик» показывает каждое исходящее соединение и интерфейс, через который его на самом деле отправило ядро. Данные берутся из системной утилиты `nettop`, а не выводятся из правил. Раз в 2 секунды приложение делает разовый снимок (`nettop -L 1`): постоянно запущенный `nettop` занимает больше одного ядра процессора. Имена сайтов подставляются из ответов локального DNS-прокси, которые служба держит только в памяти. Если у VPN остального трафика нет своего DNS, прокси видит лишь имена из правил, и для остального трафика показывается адрес. Соединения через наши туннели подписаны названиями направлений. Запись по умолчанию выключена и включается на самой вкладке (`watchTraffic` в `RouterSettings`). Записи ведутся, пока включены и она, и маршрутизация, и хранятся только в памяти приложения, последние 1000.

**Проверки.** «Проверить сайт» (в «Проверке подключения» на «Обзоре») открывает настоящее TCP-соединение на порт 443 и определяет интерфейс по локальному адресу, который выбрало ядро. «Проверка подключения» в «Обзоре» и в меню запускается сама при старте приложения и когда VPN включился или выключился, дальше — по кнопке; с выключенным VPN тоже. Обычный HTTPS-запрос к `cloudflare.com/cdn-cgi/trace` показывает адрес и страну, с которыми вас видят зарубежные сайты, запрос к `yandex.ru/internet/api/v0/ip` — российские. Запросы идут по тем же маршрутам, что и у браузера, а интерфейс берётся из локального адреса соединения и подписывается названием направления. PF пропускает всё, что попало в поднятый туннель: маршруты отправляют туда только адреса его направления, а сокет, привязанный к туннелю, — только себя; этим пользуется ping AmneziaWG через туннель. Проверка сайта ещё и спрашивает у daemon, какое имя последним получило этот адрес: другое имя означает общий адрес CDN. Живость Xray проверяется запросом через его собственный SOCKS-вход на 127.0.0.1 со случайными портом и паролем, которые знает только служба: так проверка идёт тем же outbound, что и трафик.

**Хранение.** Профили, пароль и настройки служба хранит в `/var/db/com.vpnrouter/state.json` (владелец root, каталог `0700`, файл `0600`). Приложение передаёт их по проверенному XPC и Keychain не читает, поэтому macOS не спрашивает пароль связки ключей. Обратно в приложение пароль не передаётся, только признак «сохранён». Текст профиля приложение получает только для «Изменить профиль…». Там же лежат все подключения (`connections`) и направления. Подписка обновляется, если её использует хотя бы одно направление. Цена такого хранения: файл может прочитать любой процесс с правами root, а от кражи диска защищает FileVault. Профили, которые прежние версии хранили в Keychain, не переносятся. Старые записи `com.vpnrouter.profiles.v2` можно удалить в «Связке ключей». Временные файлы служба создаёт в `/var/run/com.vpnrouter` с правами `0600`.

**XPC.** Клиент проверяется по signing identifier плюс Team ID или отпечатку сертификата. Ad-hoc сборка выставляет `VPNROUTER_ALLOW_UNSIGNED=1` и принимает запрос от любой локальной программы. Имена сайтов из DNS-ответов служба отдаёт только проверенному клиенту, а на ad-hoc сборке это любая локальная программа.

**PF.** Последнее правило — `block drop out quick all` на всех интерфейсах, поэтому всё, что Коммутатор не разрешил, не уходит никуда, даже через чужой интерфейс. Исключения — адреса, которые не покидают Mac или канал: link-local и multicast (`169.254/16`, `224/4`, `fe80::/10`, `ff00::/8`) пропускаются на любом интерфейсе до правил направлений, ULA (`fc00::/7`) — после них, чтобы VPN с такими сетями сохранил kill switch. Без этого Xcode не видел бы iPhone: CoreDevice ходит к нему по ULA через свой `utun` и по link-local через USB-интерфейс.

**Маршруты.** Маршруты по умолчанию (`0/1` и `128/1`) ведут в туннель остального трафика. Маршрут, который уже существует при добавлении, считается своим и удаляется при выключении. Это цена восстановления после падения службы: она не помнит установленные маршруты, и без этого следующий запуск падал бы на первом же из них. Включённую маршрутизацию служба сама поднимает при первом событии сети после своего перезапуска. Неудачный запуск повторяется только в другой сети, а не по кругу в той же.

## Тесты

```sh
make test
```

Тесты покрывают приоритет направлений по порядку, миграцию настроек и `state.json` от 1.0.7, экспорт и импорт направлений, направления по умолчанию и приоритет рабочих сайтов, урезание TTL и разбор `netstat`, IDN, IPv4/IPv6 CIDR, оба импортёра, DNS compression/A/AAAA/CNAME/TTL и канонизацию IPv6, сборку SERVFAIL, выбор upstream DNS по классам и список failover, MTU из AWG-профиля, fail-closed PF policy с исключением для link-local и ULA, идемпотентность и rollback маршрутов с подменённым command runner, разбор `networksetup -listnetworkserviceorder`. `swift test` не запускает службу и не меняет системную сеть.

Реальные end-to-end проверки требуют тестовых OpenVPN/AWG endpoints и выполняются на отдельном Mac, поскольку меняют PF и таблицу маршрутизации.
