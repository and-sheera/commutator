# Commutator: разработка и релизы

Пользовательская документация — в [README.md](README.md). Черновики, планы и разборы для себя кладите в `local/`: эта папка в `.gitignore`, в репозиторий она не попадает.

## Подготовка Mac (один раз)

```sh
xcode-select --install          # если нет Xcode
brew install go automake pkg-config openssl@3 lzo lz4 gh
gh auth login                   # вход в GitHub, откроется браузер
```

## Выпустить релиз

```sh
make version V=1.0.7            # 1. новая версия
git commit -am "Commutator 1.0.7" && git push   # 2. в git
make release NOTES="Что нового"  # 3. сборка и публикация
```

Установленные копии узнают о релизе сами: при запуске и раз в 6 часов они спрашивают `api.github.com/…/releases/latest`, показывают уведомление и плашку, а по кнопке ставят новый pkg. Подробнее в разделе [«Обновление из приложения»](#обновление-из-приложения).

**Шаг 1.** `make version` меняет версию сразу в обоих местах, где она живёт: в `Config/AppInfo.plist` (плюс номер сборки +1) и в `VPNRouterVersion.current` в `Sources/VPNRouterCore/Models.swift`. Если версии расходятся, приложение при каждом запуске переустанавливало бы системную службу с паролем, поэтому сборка pkg такое не пропустит.

**Шаг 2.** Коммит и push остаются за вами: релиз публикуется ровно из того кода, что лежит на GitHub.

**Шаг 3.** `NOTES` — описание релиза для пользователей. Его видно на странице Releases и в приложении по кнопке «Что нового», поэтому пишите по-русски и для людей, а не для разработчиков. Пишите коротко: что нового и что исправлено. Работает Markdown, для многострочного текста используйте `NOTES="$(cat local/заметки.md)"`. Остальное `make release` делает сам:

1. Создаёт сертификат подписи «Commutator Local Development», если его ещё нет. При первом запуске macOS попросит пароль от связки ключей. Зачем он нужен — в разделе [«Подпись»](#подпись).
2. Собирает движки (openvpn, amneziawg-go, awg, xray), только если их нет или в `scripts/build-vpn-tools.sh` поменялась версия. Первый раз это займёт минут десять.
3. Прогоняет тесты.
4. Собирает `Build/Commutator.app` и упаковывает его в `Build/Commutator.pkg`. Попутно проверяет, что сборка подписана и версии совпадают.
5. Проверяет, что всё закоммичено и запушено.
6. Публикует GitHub Release.

### Как pkg попадает в GitHub Releases

```mermaid
flowchart LR
    M["make release<br/>на вашем Mac"] --> P["Build/Commutator.pkg"]
    P -- "gh release create v1.0.7" --> R["GitHub Release v1.0.7<br/>тег v1.0.7 на вашем коммите"]
    R --> L["…/releases/latest/download/Commutator.pkg<br/>ссылка из README"]
    L --> F["пользователь скачивает"]
```

Последний шаг выполняет `gh`, консольный клиент GitHub. Он создаёт на GitHub релиз `v1.0.7`, ставит тег `v1.0.7` на текущий коммит и прикладывает к релизу файл `Commutator.pkg`. Описанием релиза становится текст из `NOTES`. Имя файла одинаковое во всех версиях, поэтому ссылка `releases/latest/download/Commutator.pkg` в README всегда ведёт на самую свежую.

Без `gh` то же можно сделать руками. Выполните `make installer`, откройте на GitHub **Releases → Draft a new release**, впишите тег `v1.0.7`, перетащите `Build/Commutator.pkg` в поле для файлов и нажмите **Publish release**.

### Первая публикация

```sh
git init -b main
git add . && git status          # не должно быть .build, Build, Vendor/sources, local/
git commit -m "Commutator 1.0.6"
gh repo create commutator --public --source . --push
make release NOTES="Первый публичный выпуск"
```

## Команды

| Команда | Что делает |
|---|---|
| `make release` | Всё от сборки до публикации, см. выше |
| `make version V=x.y.z` | Поднять версию в обоих местах |
| `make test` | Тесты. Сеть и системную службу не трогают |
| `make app` | Собрать `Build/Commutator.app` |
| `make install` | Поставить сборку себе в `/Applications`, пароль один раз. Запущенный Коммутатор сначала закрывается |
| `make installer` | Только собрать `Build/Commutator.pkg`, ничего не публикуя |
| `make tools` | Принудительно пересобрать движки |
| `make setup-signing` | Создать сертификат подписи, если его нет |
| `make icon` | Пересобрать иконку из `Config/IconArtwork.png` |

В интерфейсе macOS (Finder, Dock, меню, системные запросы) приложение называется «Коммутатор»: это имя задаёт `Config/ru.lproj/InfoPlist.strings`. Файл при этом остаётся `Commutator.app`, потому что латинский путь нужен установщику и скриптам. `CFBundleDisplayName` в `Config/AppInfo.plist` должен совпадать с именем файла, иначе Finder не подставит русское имя.

`BUNDLE_ID` по умолчанию `com.vpnrouter.app` и переопределяется при сборке. Внутренние идентификаторы (`com.vpnrouter.*`, `VPNRouter*`, `VPNROUTER_*`) остались от прежнего названия и специально не меняются: иначе обновление поверх установленной версии сломается.

## Подпись

Без сертификата сборка получается ad-hoc, и системная служба принимает команды от любой программы на Mac. Поэтому `make installer` и `make release` такую сборку не упакуют. Для своей машины она годится: `make install` работает и без сертификата, только «Изменить…» профиля будет каждый раз спрашивать пароль администратора.

С сертификатом служба проверяет, что команду прислал именно Коммутатор. Она сверяет отпечаток сертификата из подписи, а не доверие к нему, поэтому проверка работает и на чужом Mac, где этот сертификат никому не известен. Для Gatekeeper сборка остаётся неподписанной: отсюда шаг «Всё равно открыть» при установке.

**Сохраните копию сертификата:** «Связка ключей» → «Commutator Local Development» → «Экспортировать…» → `.p12`. Если он потеряется, `make release` создаст новый с другим отпечатком. Установка pkg поверх это переживёт, но macOS может заново спросить у пользователей разрешение на уведомления, а кнопка обновления в приложении откажется ставить такой релиз: этот один раз пользователям придётся поставить pkg вручную. Чтобы собирать на другом Mac, импортируйте туда `.p12`.

## Движки

Пользователям ничего собирать не нужно: всё уже внутри pkg. Сборка движков — аналог `npm install`, но нужна только вам и только один раз на версию. Готовых пакетов для этого нет: openvpn под macOS официально распространяется только исходниками, а версия из Homebrew зависит от библиотек Homebrew, которых у пользователей нет. `scripts/build-vpn-tools.sh` собирает статические arm64-бинарники из закреплённых тегов и кладёт рядом архивы исходников, как того требует GPL.

**Обновить движок:** поменяйте тег в `scripts/build-vpn-tools.sh` и в [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md). `make release` сам пересоберёт движки и остановится на незакоммиченном `Vendor/SHA256SUMS`: закоммитьте его, запушьте и запустите `make release` ещё раз.

## Иконка

Исходная картинка лежит в `Config/IconArtwork.png` (квадрат с прозрачным фоном). `scripts/make-icon.swift` кладёт её на светлую скруглённую плашку по сетке иконок macOS. Размер картинки на плашке задаёт `artworkSide` в начале скрипта. После замены картинки или правки скрипта выполните `make icon`. Результат (`Config/AppIcon.icns`, `Config/AppIcon.png` для README) коммитится.

## Что делает установщик

Системная служба и VPN-бинарники входят в сам `.app`. Postinstall пакета копирует службу в `/Library/PrivilegedHelperTools/com.vpnrouter`, регистрирует её в launchd, снимает карантин с приложения и запускает его от имени вошедшего пользователя. Всё это происходит внутри той единственной авторизации, которую запросил установщик macOS.

Если приложение скопировали в `/Applications` вручную, минуя pkg, оно поставит службу само при первом запуске и спросит пароль. Если его скопировали поверх старой версии, при запуске оно заметит службу другой версии и заменит её. Если установку отменили, в окне будет кнопка «Установить…». Сборка с Developer ID вместо этого регистрирует службу через `SMAppService` (System Settings → General → Login Items).

### Обновление из приложения

Приложение проверяет `releases/latest` при запуске и раз в 6 часов (`AppModel.watchUpdates`). Сравнение версий и разбор ответа — `AppRelease` в Core. Черновики и pre-release GitHub сюда не отдаёт, релиз без `Commutator.pkg` не предлагается. Каждый шаг — кнопка пользователя:

1. «Скачать» кладёт pkg и описание в `~/Library/Caches/<bundle id>/Update`. Скачанное переживает перезапуск приложения и удаляется, когда версия установлена.
2. «Обновить и перезапустить…» спрашивает, можно ли выключить VPN, и выключает его через старую службу, как обычный переключатель. Уборка туннелей, PF и DNS не зависит от 20 секунд, которые launchd даёт службе при остановке. Затем приложение перестаёт опрашивать службу и отправляет ей `installUpdate` с путём к pkg. Пароль не нужен: ставит служба (`RouterDaemon.installUpdate`), она уже работает от root. Служба:
   - принимает запрос только от клиента с подписью Коммутатора (обычная проверка XPC);
   - отказывает, пока предыдущая установка ещё идёт;
   - копирует pkg в `/var/db/com.vpnrouter/update` (доступ только у root) и распаковывает его. Символическая ссылка в распакованном pkg — отказ: через неё проверку можно направить в папку пользователя;
   - сверяет подпись Commutator.app с тем же требованием, по которому проверяет клиента (identifier плюс отпечаток сертификата или Team ID);
   - ставит только версию новее своей, без откатов назад;
   - запускает `install-update.sh` из **проверенного** бандла разовой задачей launchd `com.vpnrouter.update`. Скрипты самого pkg не выполняются. Отдельная задача нужна потому, что скрипт вызывает `install-system-component.sh`, а тот останавливает службу, и её дочерний процесс погиб бы вместе с ней.

   Скрипт копирует приложение во временную папку со случайным именем в `/Applications`, отодвигает старое и ставит новое на его место. Если что-то сорвалось, старое возвращается. Затем скрипт ставит новую службу, запуская `install-system-component.sh` из проверенной копии, а не из `/Applications`: туда может писать любой процесс администратора. Старое приложение ждёт, пока ответит служба новее его самого (до трёх минут), затем выходит и открывает новое. Пока идёт установка, приложение не шлёт службе настройки, профили и переключатель. Обновляется только копия `/Applications/Commutator.app`: копию в другом месте кнопка не обновит, она предложит pkg. Новое включает VPN, если стоит отметка `resume-after-update` в UserDefaults.

Безопасность держится на подписи. Кто получит сертификат «Commutator Local Development», сможет поставить что угодно на все Mac с Коммутатором без пароля, поэтому храните `.p12` так же бережно, как ключ. Ad-hoc сборку служба так не обновляет, у неё нет требования к подписи. Новая служба читает `state.json` старой, поэтому новые поля в нём только необязательные.

Кнопка «Удалить Коммутатор…» (внизу «Общих») просит службу удалить всё без пароля (`RouterDaemon.uninstall`). Служба принимает запрос только от подписанного клиента, удаляет только `/Applications/Commutator.app` (путь сверяется после раскрытия ссылок), сверяет его подпись и запускает разовую задачу launchd `com.vpnrouter.uninstall`. Задача выполняет копию `scripts/uninstall.sh`, которую `install-system-component.sh` кладёт в `/Library/PrivilegedHelperTools/com.vpnrouter`, куда пишет только root. Отдельная задача нужна потому, что служба при остановке пишет журнал и сохраняет состояние, и удалённые файлы появились бы снова. Перед этим приложение выключает VPN через службу, как при обновлении. Если служба отказала (ad-hoc сборка, служба старой версии или её нет, копия не в «Программах», служба зарегистрирована через SMAppService и копии скрипта рядом нет), приложение запускает `uninstall.sh` из бандла с паролем администратора. Скрипт останавливает службу (по SIGTERM она сама возвращает DNS, PF и маршруты) и удаляет всё, что поставил установщик. Новый системный файл — добавьте его туда же.

## Устройство

- `VPNRouterApp` — окно, меню, уведомления и XPC-клиент.
- `VPNRouterDaemon` — root-служба: management-сокет OpenVPN, проверка handshake AmneziaWG, Xray и подписки, DNS-прокси, свои маршруты и PF anchor `com.apple/vpn-router`.
- `VPNRouterCore` — модели, разбор профилей, DNS и CIDR, чистый генератор правил PF.

Рабочее правило имеет приоритет над `direct` при любом совпадении, даже если `direct`-правило точнее: `corp.example.com` в рабочих бьёт `www.corp.example.com` в direct.

**DNS** раскладывается по тем же классам: рабочие имена уходят в рабочий DNS (его присылает сервер OpenVPN) через туннель, `.ru`, `.su`, `.рф` и исключения — в DNS текущей сети, остальные — в DNS из AWG-профиля через личный туннель. Последнее включается автоматически, если в AWG-профиле задан `DNS =`. Тогда системный resolver на время работы переключается на локальный прокси и восстанавливается при выключении. Если переключить resolver не удалось, включение завершается ошибкой и откатывается целиком: иначе статус «Работает» показывался бы, пока имена по-прежнему уходят в DNS сети.

Локальный прокси слушает `127.0.0.1:53`: `networksetup -setdnsservers` принимает только адрес без порта, поэтому другого способа увести системный resolver на прокси нет. Если порт занят чужим резолвером, включение завершится ошибкой, а системный DNS останется нетронутым. В каждом классе перебираются до двух серверов: если первый не ответил за 2 секунды, запрос уходит второму, и только потом клиент получает SERVFAIL. Третий и следующие серверы не используются. С `DNS =` в AWG-профиле прокси отвечает SERVFAIL, пока туннель не поднялся, а не спрашивает DNS текущей сети.

**Журнал.** Полный журнал подключений служба пишет в `/var/log/vpn-router.log` (root, `0600`; при 8 МБ обрезается с сохранением свежей половины): вывод openvpn, amneziawg-go и xray, обмен с management-сокетом, шаги запуска и остановки, причины падений туннелей, раз в полминуты — строка состояния. Движок личного VPN запускается с `LOG_LEVEL=verbose`, иначе он молчит и по логу нельзя отличить рукопожатие без ответа от пакета, который зарубил наш же PF; строки про keepalive отбрасываются при чтении. Последние 10 000 строк видны вживую в «Диагностике», вкладка «Журнал».

**Обезличивание журнала.** Журнал пишется, чтобы его отправляли на разбор, поэтому `LogRedactor` (в Core, тестируется) заменяет имена серверов и публичные адреса устойчивыми псевдонимами `хост#N` и `адрес#N`: один и тот же адрес всегда получает тот же псевдоним, поэтому маршрут, правило PF и рукопожатие по-прежнему связываются между собой. Почта и поля сертификатов скрываются целиком, длинные ключи обрезаются до четырёх символов. Имена заменяются только зарегистрированные (`TunnelLog.register(host:)` — серверы профилей, endpoint личного VPN, хост подписки), иначе под замену попали бы `com.vpnrouter` и `openvpn.conf`. Частные адреса, имена интерфейсов, маски сети, порты и коды ошибок остаются как есть — без них журнал бесполезен. `VPNROUTER_LOG_RAW=1` отключает обезличивание, только для ad-hoc dev-сборки. Имена сайтов, которые резолвит пользователь, в журнал не попадают вообще: это была бы история посещений.

**Сон и пробуждение.** Отдельных системных уведомлений о сне служба не слушает: сигналом служит событие сети, а сам факт сна виден по разрыву между тиками обслуживания («Похоже, был сон»). После пробуждения последнее рукопожатие AmneziaWG всегда просрочено, поэтому запас в 35 секунд отсчитывается не от запуска туннеля, а от момента, когда рукопожатие впервые оказалось просроченным — WireGuard успевает восстановиться сам, без перезапуска движка. Для OpenVPN ограничение на подключение взводится заново при каждом мягком перезапуске (90 секунд): иначе переподключение после пробуждения могло висеть бесконечно, и никто за ним не следил.

**Трафик.** Вкладка «Трафик» показывает каждое исходящее соединение и интерфейс, через который его на самом деле отправило ядро. Данные берутся из системной утилиты `nettop`, а не выводятся из правил. Раз в 2 секунды приложение делает разовый снимок (`nettop -L 1`): постоянно запущенный `nettop` занимает больше одного ядра процессора. Имена сайтов подставляются из ответов локального DNS-прокси, которые служба держит только в памяти. Без `DNS =` в AWG-профиле прокси видит лишь имена из правил, и для остального трафика показывается адрес. Запись по умолчанию выключена и включается на самой вкладке (`watchTraffic` в `RouterSettings`). Записи ведутся, пока включены и она, и маршрутизация, и хранятся только в памяти приложения, последние 1000.

**Проверки.** Проверка на странице «Маршруты» открывает настоящее TCP-соединение на порт 443 и определяет интерфейс по локальному адресу, который выбрало ядро. «Проверка подключения» в «Обзоре» запускается сама, как только VPN подключился, дальше — по кнопке. Запрос к `cloudflare.com/cdn-cgi/trace` показывает адрес и страну, с которыми вас видят сайты .com, запрос к `yandex.ru/internet/api/v0/ip` — адрес для сайтов .ru. Ping через интерфейс OpenVPN до рабочего DNS проверяет рабочую сеть. Живость Xray проверяется запросом через его собственный SOCKS-вход на 127.0.0.1 со случайными портом и паролем, которые знает только служба: так проверка идёт тем же outbound, что и трафик.

**Хранение.** Профили, пароль и настройки служба хранит в `/var/db/com.vpnrouter/state.json` (владелец root, каталог `0700`, файл `0600`). Приложение передаёт их по проверенному XPC и Keychain не читает, поэтому macOS не спрашивает пароль связки ключей. Обратно в приложение пароль не передаётся, только признак «сохранён». Текст профиля приложение получает только для «Изменить…». Кроме текущих профилей AmneziaWG и Xray там же лежат запасные профили личного VPN (`spares`): новый профиль отправляет прежний в запас, а выбор другого профиля меняет их местами. Подписки из запаса не обновляются. Цена такого хранения: файл может прочитать любой процесс с правами root, а от кражи диска защищает FileVault. Профили, которые прежние версии хранили в Keychain, не переносятся. Старые записи `com.vpnrouter.profiles.v2` можно удалить в «Связке ключей». Временные файлы служба создаёт в `/var/run/com.vpnrouter` с правами `0600`.

**XPC.** Клиент проверяется по signing identifier плюс Team ID или отпечатку сертификата. Ad-hoc сборка выставляет `VPNROUTER_ALLOW_UNSIGNED=1` и принимает запрос от любой локальной программы. Имена сайтов из DNS-ответов служба отдаёт только проверенному клиенту, а на ad-hoc сборке это любая локальная программа.

**Маршруты.** Маршрут, который уже существует при добавлении, считается своим и удаляется при выключении. Это цена восстановления после падения службы: она не помнит установленные маршруты, и без этого следующий запуск падал бы на первом же из них. Включённую маршрутизацию служба сама поднимает при первом событии сети после своего перезапуска. Неудачный запуск повторяется только в другой сети, а не по кругу в той же.

## Тесты

```sh
make test
```

Тесты покрывают приоритет рабочих правил, IDN, IPv4/IPv6 CIDR, оба импортёра, DNS compression/A/AAAA/CNAME/TTL и канонизацию IPv6, сборку SERVFAIL, выбор upstream DNS по классам и список failover, MTU из AWG-профиля, fail-closed PF policy, идемпотентность и rollback маршрутов с подменённым command runner, разбор `networksetup -listnetworkserviceorder`. `swift test` не запускает службу и не меняет системную сеть.

Реальные end-to-end проверки требуют тестовых OpenVPN/AWG endpoints и выполняются на отдельном Mac, поскольку меняют PF и таблицу маршрутизации.
